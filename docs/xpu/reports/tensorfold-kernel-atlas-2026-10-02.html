Assessment · source-backed design inference

Build the same serving engine around kernels designed for Xe2.

TensorFold’s strongest ideas transfer: reuse compressed weights across a verify window, fuse small operators, keep recurrent state resident, and make the target’s arithmetic independent of the other rows. PyTorch XPU, Intel Triton and native SYCL provide suitable implementation routes. Comparable optimization is feasible; comparable end-to-end speed remains a hardware experiment.

One round, three layers

How the kernels connect to the engine

02 / 13

A target forward evaluates several proposed rows in one call. Only tokens matching the target’s own serial rule survive. The optimization comes from performing useful target work together while retaining independent arithmetic and state.

1
Prompt & prefix state

Chunked prompt GEMM, GDN chain and causal attention produce a prompt-end state.

prefill → qmm_prefill + gdn_prefill + prompt attention

Prompt arithmetic is a separate contract. Fresh and resumed prompts must retain identical chunk behavior; decode state cannot be substituted blindly.

2
Draft a small tree

DFlash2 uses committed target taps; context copies can also supply proposals.

dflash2 + draft_attention → draft_tree

A cheaper quantized drafter and vocabulary-row subsets cut proposal cost. Tree allocation uses expected token gain versus measured forward cost.

3
Verify every layer

Residual/norm → packed projections → GDN tree or tree attention → gated output / MLP.

glue → qmm → gdn / attention → glue → qmm

Qwen’s target has 48 GDN and 16 attention layers. Each query sees committed keys plus its own tree ancestors. Each recurrent node starts from its parent’s state.

4
Sample & commit

Target samples decide the accepted path; GDN replay and KV/conv tails retain only that path.

sampling → commit / pending replay → next round

Several streams can share a forward while retaining separate caches. Dense Qwen’s CUDA path does not rely on CUDA graphs.

Why TensorFold can be fast

03 / 13
01

Read compressed weights in place

Decode operates on packed codes; scales and bias correction are applied inside the accumulation loop. A full BF16 model is not materialized for each decode pass. That saves bandwidth and working-set size.

02

Make a verify window worth its cost

Several proposed tokens reuse a weight tile. A row retains the same target arithmetic as a serial step, enabling exact acceptance while converting a bandwidth-limited GEMV into a more useful small matrix operation.

03

Fuse boundaries, preserve roundings

Residual+norm+group sums; expert up+activation; norm+RoPE; and combine+residual reduce dispatches and intermediate traffic. Fusions keep the rounding points of the unfused contract.

04

Keep recurrent state close to compute

GDN and SSM scans keep state tiles in registers while advancing several tokens. Tree scratch and accepted-path replay avoid copying a complete state for every candidate or spilling it after every step.

05

Group sparse work by expert

Routing creates stable row/slot lists per expert. The compute kernel reuses compressed weights over those pairs and handles activation epilogues. The prompt and decode plans use different item widths.

Optimize the entire round

Subset draft heads, confidence stops, cache reuse, asynchronous work, graphs where supported and cost-aware round allocation reduce work outside the target kernels. A faster microkernel alone does not ensure a faster response.

Native extensions + Triton

CUDA kernel atlas

04 / 13

CUDA is a mixed implementation: native CUDA C++ for compressed compute, recurrence and prompt attention; Triton for glue, tree/latent attention, routing and sampling; PyTorch for orchestration. Open a group for its operation, optimization and Intel interpretation.

01Shared · Native CUDAPacked INT4 decode & grouped projectionsArchitecture rewrite

qmm.cu runs group dots with integer-valued BF16 codes, then applies scale and input-sum bias correction in FP32. qmm_group.cu combines up to four projections of the same input on SM 12.x; it is a newer optimization than the fork baseline.

Why it saves work

Weights are packed once into NVIDIA fragment order. cp.async stages inputs and weights; ldmatrix and BF16 MMA feed the tensor cores. K splits depend on the weight shape. Cluster peers, or a separate reducer, add partials in slice order. Grouped projections and programmatic dependent launches reduce launch and dependency latency.

Intel interpretation proposal

K4 · high priority. Build a symmetric W4A16 Triton baseline for g64/g128 and both scale dtypes. Repack for Xe2 2D loads, use SG16 DPAS or a fixed-order vector GEMV, and reduce split-K in a second pass. Grouped projection launches are a later fusion candidate.

02Shared · Native CUDAPrompt INT4 GEMM & optional FP8Prompt rewrite

qmm_prefill.cu rounds affine weights to BF16 inside the operand path and runs one FP32 K chain. The separate FP8 prompt kernel uses row-scaled e4m3 activations. Prompt arithmetic is chunk invariant, but differs from decode arithmetic.

Why it saves work

Large tiles reuse weights across many prompt rows. Shared-memory swizzles avoid bank conflicts; multistage copies overlap memory with MMA. Decode avoids materializing the full dequantized model, and prefill also decodes its operands locally.

Intel interpretation proposal

K5 · Triton dequant + BF16 dot first; native DPAS only after profiling. Preserve a fixed prompt accumulation chain. The fork refuses --prefill-fp8 on XPU; a software FP8 conversion is not a corresponding Xe2 hardware acceleration path.

03Qwen dense · Native CUDAGDN tree, replay & prompt chainsCorrectness critical

gdn.cu keeps an FP32 state tile resident while it walks a tree schedule. Branch slots preserve parent states; replay folds only the accepted path into committed state. gdn_prefill.cu stages several prompt rows ahead and scans with its own chunk-stable arithmetic.

Why it saves work

Each state tile is read and written around a sequence of steps rather than spilled after every token. Tree scratch is limited to the live branch schedule. The latest source also supports pending accepted rows in its tree kernel, so the older separate-replay map is not the only upstream path.

Intel interpretation proposal

K1 · a missing portable implementation. Use one shared step body for serial, tree and replay. SG16 can cover dk=128 with eight values per lane; explicit reductions and a register/SLM budget are essential. A small native SYCL implementation is useful if persistent-state Triton fails on the pinned stack.

04Shared · Native CUDAGrouped-query prompt attentionPortable reference exists

prefill_attention.cu reproduces the Triton reference arithmetic while sharing staged K/V between several query heads of one KV head. The wrapper currently dispatches D=64 to Triton and D=128/256 to native CUDA.

Why it saves work

An online softmax retains only the running maximum, normalizer and output. Head grouping saves K/V reads; fixed absolute-position key tiles preserve prompt chunk boundaries. This is a custom implementation of a familiar attention algorithm, not a dense score-matrix allocation.

Intel interpretation proposal

K6 · the existing triton_attention entry is the first XPU route for all supported head dimensions. Tune registers and operand loads. Native flash attention is optional if it becomes a measured bottleneck.

05Shared · Native CUDAMoE plan, packed experts & epiloguesLarge rewrite

experts.cu groups (token, expert-slot) pairs into expert items, runs the up/gate and down operations, and supports ReLU² or SwiGLU epilogues. Separate pack and prompt kernels share a stable pair plan.

Why it saves work

Grouping amortizes an expert weight load over its assigned rows. Decode double-buffers register loads and uses a weight cache hint. Up activation is fused. Prompt items are wider than decode items; unused items exit without a host count read.

Intel interpretation proposal

K3 · Nemotron’s largest missing compute block. Start with an integer stable grouping plan and Triton grouped GEMV/GEMM. Implement an Intel weight layout; do not copy the CUDA fragment layout. Keep expert and slot sums ordered and ties stable.

06Nemotron · Native CUDAMamba-2 prompt scanMissing prompt kernel

scan_rows.cu advances the FP32 SSM state in prompt order, computes dt/decay and the readout, and rounds at explicit BF16 boundaries. It is distinct from Nemotron’s Triton decode/replay scan.

Why it saves work

A block owns value rows, loads state into registers and stages B/C and token data in shared memory in groups of 16. Only the final state is written back, reducing state traffic across a long prompt.

Intel interpretation proposal

K2 · write a chunk-invariant scan. Fixed-order vector arithmetic fits SYCL well; persistent registers must stay within the occupancy budget. Use the source’s rounding contract rather than an algebraically reassociated parallel scan.

08Shared · Native CUDAEXL3 trellis linears & expertsDeferred format

EXL3 decodes codebook/trellis tiles directly for linears and grouped experts, with Hadamard rotations around the products. Codebook-specific translation units instantiate the shared expert implementation. Prompt code reconstructs a weight matrix for a chunk, then applies a fixed-tile GEMM.

Why it saves work

Very low stored bits reduce weight traffic. Decode maps reconstructed values into MMA operands and keeps rotations and split reductions ordered. Fused expert epilogues remove intermediate launches.

Intel interpretation proposal

WS10 · later, outside the initial symmetric INT4 backend. Port decoding and rotations separately from the matmul. Preserve license notices; do not infer row invariance from another Intel engine’s deterministic GEMV alone.

09Shared · Native CUDANVFP4 / FP8 W4A16-style pathsDeferred format

qmmf.cu and prompt.cu decode FP4/FP8 weights into BF16 operands. NVFP4 experts use the shared pair plan. These are distinct from the checkpoint-native FP4/FP8 activation kernels added later.

Why it saves work

Block-scale application is folded into the compute loop and K splits stay ordered. On architectures without a given native low-precision MMA, BF16 operands provide a fallback arithmetic route.

Intel interpretation proposal

The concept of software decoding is transferable, but the initial XPU format policy refuses these checkpoints. There is no reason to build these before g64/g128 symmetric INT4 and the two target recipes are correct.

10Shared · Native CUDACheckpoint-native low precision & bulk GEMMHardware-specific

Newer native kernels quantize activations, run FP4×FP4 on SM 12.x or FP8×FP8, fuse gate/up with SwiGLU and output quantization, and provide a bulk-copy prompt GEMM.

Intel interpretation proposal

18Qwen dense · MLX / MetalM5 tensor-unit linearsTransfer the strategy

lane_qmm.py uses MetalPerformancePrimitives matmul2d operations with packed codes. It tiles weights, pairs scale/bias data, and fixes K splits by shape. lane_fuse.py stacks compatible projections and consumes strided results in place.

Why it saves work

Small verify windows share packed weight reads on matrix hardware. Source-hashed kernels and baked constants avoid repeated template parsing. Wider cooperative tiles are used where supported, while preserving the per-output arithmetic.

Intel interpretation proposal

The performance strategy maps to Intel XMX, but MPP tensor descriptors, SIMD fragment indices and Metal bindings do not. Replace the entire operand/launch layout with DPAS and Xe2 2D loads.

The loader is part of the optimization.

The chosen Intel checkpoints use GPTQ/AutoRound or compressed-tensors layouts, unlike the MLX affine checkpoints read by upstream A/B. Validate symmetric INT4, g64/g128 and identity grouping; derive the zero point from sym; preserve scale dtype; honor modules left at BF16; and stream repacking per tensor. A correct compute kernel with a wrong zero point is still a broken engine.

w = s · (q − 8) = s · q + b, with b = −8 · s
P_g = dot(x_g, q_g); xs_g = sum(x_g)
CUDA decode contract: acc = fma(xs_g, b_g, fma(P_g, s_g, acc))
Algebra does not define floating-point bits. SYM weights fit this affine structure, and widening FP16/BF16 scales to FP32 is exact. Preserve scale values and explicit operation/rounding order; do not claim that an arbitrary dequantize-then-GEMM implementation is bit-identical to this groupwise decode.   • No floating-point atomic reductions.
  • Fixed split-K and ordered slice/rank/slot sums.

XPU output need not match CUDA or MLX bit for bit. It must match XPU serial execution for the same engine, weights and settings.

Upstream varies some row tile sizes after equivalence checks. The fork’s rule is stricter: XPU split-K, tiles, subgroup size, GRF mode and num_warps are weight-shape choices rather than runtime row-count autotuning.
